The goal: scale read replicas without copying any data. Instead of duplicating the dataset to every replica, we keep one physical copy on a shared volume and let up to 16 machines read it — measured at 242 thousand reads a second on AWS with RocksDB. Let's start with why this is hard.

Normally, scaling reads means replicating or sharding — and both copy the dataset everywhere and keep the copies in sync forever. RocksDB makes the pain obvious: one process, one exclusive lock on its files. So the real question is: what if we didn't copy at all?
01The problem

Scaling reads usually means copying data.

When read traffic outgrows one box, the usual fixes — replicate or shard — copy the dataset to every replica and keep the copies in sync forever. RocksDB makes the pain concrete: an embedded key-value store, a library inside one process, holding an exclusive lock on its files.

Single process
No network server, no built-in way for another machine to read the data. It lives and dies with one process on one host.
Single writer lock
Opening read-write takes an exclusive OS lock on the directory. Exactly one process, anywhere, can hold it.
Scaling means copying
Replicate (N full copies, kept in sync forever) or shard (routing layer + rebalancing). Both move data and add moving parts.

Replication time grows with dataset size · storage cost grows linearly with replicas.

The reframe: every machine reads the same files. EBS Multi-Attach shares one volume across 16 instances, GFS2 lets them all mount it safely, and RocksDB secondaries read it lock-free, catching up every ten milliseconds. So adding a reader adds compute and cache, not storage. What does that buy us?
02The reframing

What if every machine read the exact same files?

Not a copy per replica — one physical copy, visible to the whole fleet at once. Three capabilities make that safe.

AWS EBS Multi-Attach
One io2 volume attaches to up to 16 EC2 instances simultaneously. Every instance sees the same block device.
Linux GFS2
A cluster filesystem built for many machines mounting one disk with coherent, real-time file visibility — where ext4/XFS would corrupt instantly.
RocksDB Secondaries
Open the same directory read-only, no writer lock, and call TryCatchUpWithPrimary() every ~10 ms.
The result: 1 writer + up to 15 readers, all reading one disk. Adding a reader adds compute and cache — not storage. There is still only one copy of the data. RocksDB is the example; the EBS Multi-Attach + cluster-FS blueprint applies to any read-heavy store with a read-only / follower open path.
Four wins: a new reader is live in about five minutes at any data size, storage stays flat, throughput scales nearly linearly — fifteen thousand reads a second on one node up to 242 thousand on sixteen — and readers stay about ten milliseconds fresh. Here's how it's wired together.
03Why it matters

Read scale-out that doesn't grow with your data.

Onboarding is constant-time
A new reader is live in ~5 minutes — 1 GB or 1 TB, same time. No dataset copy.
Storage cost is flat
One volume, not one-per-replica. 1 TB across 16 readers is still 1 TB.
Throughput scales with nodes
Read capacity grows ~linearly: each node serves reads from its own CPU + cache over the one shared copy. ~15K reads/sec on 1 node → ~242K on 16 (~16×), zero errors.
Fresh + elastic
Readers catch up in ~10 ms; a new reader is live in ~5 min; promote a reader to writer in ~1.5 min.
The whole system: a load balancer fans reads across every node — reads only; writes and admin are blocked. One writer, many read-only secondaries, all mounting one GFS2 filesystem over a single volume. The cluster software underneath keeps it safe, off the data path. Let's see it as layers.
04Architecture

One load balancer, one disk, one copy of the data.

As a stack: shared block storage at the bottom, the GFS2 cluster filesystem above it, then the coordination layer for membership and fencing, and RocksDB on top. Each layer depends on the one below. So how does a write actually reach the readers?
05The stack

Four layers, each depending on the one below it.

Boot order follows the dependency: Corosync → Pacemaker → DLM → GFS2 mount → RocksDB service.

4

The key to freshness: the writer flushes a new file to the shared disk, and readers re-read those physically identical files — no network replication — catching up in about ten milliseconds. Same bytes, no copy. And since reads spread across the fleet, the fleet has to flex in size.
06Data flow

A write reaches every reader in about ten milliseconds.

No network replication of data — readers re-read the writer's physically identical files on the shared filesystem.

Four operations, all while staying available: scale up adds a reader in about five minutes, scale down leaves cleanly, promote fails over in about ninety seconds, and kill triggers fencing plus an automatic replacement. The writer keeps serving throughout. Here's the operator's view.
07Elasticity & failover

The fleet changes size while staying available.

scale up Add readers
Raise ASG desired → boot → tag rocksdb-join → watcher joins it → GFS2 mounts → serving. A single new reader is live in ~5 min (mostly EC2 boot); in a bulk scale the writer joins each ~40 s/node after boot.
scale down Remove readers
Lower desired → shutdown hook leaves the cluster cleanly → watcher purges config → journal recovered. ~3 min for a full 16→1.
promote Failover
Old writer demoted in place; target reader drops the LOCK, reopens read-write, starts the watcher. ~1.5 min — data already mounted.
kill Recover
Node lost → Corosync detects → Pacemaker fences via EC2 API → journal recovered → ASG relaunches a replacement. ~5–7 min — a fresh EC2 boot + rejoin.

The writer and existing readers stay available throughout a full 1→16 scale-out (~14 min end-to-end).

It's all driven from one terminal dashboard — live nodes, volume stats, real-time metrics, and a command line for scale, promote, read, write, and stress-test. Let's push it to the limit.

This is built for one job — fanning out reads over a large, cacheable dataset, not general-purpose Highly Available infrastructure. The edges: single AZ, one shared volume as a failure domain, a single writer, and a sixteen-node ceiling. Know them before you reach for it. A quick word on security.
11Honest trade-offs

Purpose-built for one job — with deliberate limits.

This fans out reads over a large, cacheable dataset. It is not a general-purpose HA database. Know the edges.

AZ Single Availability Zone
Multi-Attach requires all instances in the volume's AZ. No multi-AZ resilience.
blast radius One volume
A single shared volume is a single failure domain for the whole cluster.
writes Single writer
Write throughput does not scale; the writer is the failover point.
ceiling 16 instances
A hard EBS Multi-Attach limit on read fan-out.
shared IOPS budget
All nodes share the volume's provisioned IOPS.
ops Cluster stack
Pacemaker/Corosync/DLM/fencing must stay healthy for the shared FS.
Locked down to the load balancer: the service port is ALB-only, SSH is closed in favor of SSM, and the ALB serves reads but blocks writes and admin. Admin needs a bearer token, IMDSv2 is enforced, and the volume's encrypted. The one honest gap: no TLS yet. Let me wrap up.
12Security & hardening

Locked down to the load balancer — admin actions are authenticated.

Nothing reaches a node directly: the data port is locked to the load balancer, admin endpoints require a token, and operators reach instances only through AWS SSM — no public SSH.

network Closed perimeter
Port 8080 is reachable only from the ALB (not the internet); SSH is closed — operators use SSM Session Manager; cluster traffic is scoped to members.
authz Authenticated admin
Every /admin/* and /cluster/* call needs a bearer token (SSM SecureString, fail-closed). The ALB is a read-only data plane — it returns 403 for /admin/* and for writes (/put, /delete, …), so only reads are served publicly; writes run on-box via SSM.
instance Hardened
IMDSv2 enforced (hop-limit 1); bootstrap inputs validated (no shell injection); secrets in SSM SecureString, wiped on teardown; data volume encrypted at rest; IAM scoped to least privilege; ALB access logs to S3.
honest gap No TLS yet
Traffic is plaintext HTTP — accepted for the locked-down, in-VPC network. Close it with an ACM cert or a CloudFront front-door when a domain is available.
